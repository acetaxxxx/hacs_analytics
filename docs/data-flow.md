# Data flow and report lifecycle

## Ingestion

1. The Home Assistant integration subscribes to `state_changed` for the configured scope. The default scope is all entities, with explicit excludes taking precedence.
2. Each accepted event is normalized to UTC and receives a stable `event_id` generated by the integration. A record includes entity ID, observed time, old/new state, safe metadata, and source revision.
3. Numeric entities also produce periodic snapshots. The default interval is five minutes; the entity profile may override it.
4. The integration accumulates events for up to 30 seconds or 100 events, whichever comes first. A request has a bounded timeout and does not block Home Assistant's event loop.
5. The Go ingest endpoint validates the batch, deduplicates by `event_id`, stores accepted records in one transaction, updates intervals/rollups, and returns the accepted/duplicate counts.
6. A heartbeat is sent about every minute even when no state event occurred. The sidecar closes the previous heartbeat interval. Missing heartbeats become explicit `data_gap` records.

The first release accepts data loss while the external service is unavailable. It does not put a durable event queue on the Raspberry Pi. A later version can add a durable outbox without changing the ingest contract.

## Profiles and aggregation

Profile selection is deterministic:

```text
explicit entity exclusion -> drop
explicit entity profile override -> use it
domain/device_class profile -> use it
generic profile -> use it
```

Profile changes create a new `profile_version`. Recompute reads only retained raw records (30 days). Rollups older than that remain valid under their original profile version and are not silently rewritten.

Raw observations feed:

- state transition counts and first/last seen;
- state-duration intervals, including unavailable/unknown;
- numeric min/max/average, change magnitude, and coverage;
- energy and other profile-specific counters;
- data-quality and heartbeat-gap indicators.

Daily rollups use the Home Assistant local timezone and local calendar date. UTC timestamps remain the storage truth. A report at the configured active time (default 08:00; selectable 08:00, 12:00, 18:00, or 22:00) covers the previous complete local calendar day. DST days can therefore contain 23 or 25 hours; the report carries the timezone and actual window bounds.

## Report lifecycle

The report job is keyed by `report_date`; it stores the configuration/profile snapshot used for that run. Both the scheduled trigger and manual trigger call the same idempotent command:

```text
requested -> collecting -> deterministic_ready -> ai_pending
         -> ai_running -> completed
                           \\-> ai_retry_scheduled -> ai_running
                           \\-> ai_failed
```

For a report date:

1. Query bounded daily rollups, intervals, anomalies, risks, and data-quality facts.
2. Run deterministic checks and compute evidence IDs.
3. Build a redacted aggregated DTO for Gemini; never send a raw event dump.
4. Call Gemini with the report JSON schema and Traditional Chinese language instruction.
5. Validate and normalize Gemini output. Schema failure is a failed attempt, not a partially valid report.
6. Store the complete structured report and its run metadata.
7. Home Assistant polls job status and then fetches the report.
8. The integration exposes a compact sensor state/attributes view and sends the report through the configured existing Telegram service. Telegram messages are split when the channel limit requires it.

Manual reports accept an explicit ISO local date (`YYYY-MM-DD`) and use the same idempotency semantics. A rerun creates a new run for the same date only after an explicit force operation; ordinary polling/retry never overwrites a completed report.

## Backpressure and limits

The report API returns a complete JSON document, while Home Assistant may render a compact view. The number of anomalies and suggestions has no semantic fixed cap. Technical limits still apply: SQLite query bounds, Gemini context/token limits, HTTP body limits, and Telegram message size. When a limit is reached, the system records truncation in `data_quality` and never presents an incomplete list as complete.
